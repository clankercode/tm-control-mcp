### What version negotiation requires

There are two eras. A server that advertises only `2026-07-28` follows the modern rules. Legacy rules apply only if the server also implements `initialize`.

#### Modern (`2026-07-28`): no `initialize`

Spec, “Protocol Version Negotiation” (https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning):

- There is **no negotiation handshake**. Every request carries its protocol version. The server accepts or rejects **each request independently**.
- Every request declares the version in `_meta["io.modelcontextprotocol/protocolVersion"]`. On HTTP the same value is also the `MCP-Protocol-Version` header. Header and body **MUST** match; mismatch is HTTP `400` and JSON-RPC `HeaderMismatch` `-32020`.  
  Streamable HTTP, “Protocol Version Header”: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http
- If the server does not implement the requested version, it **MUST** respond with `UnsupportedProtocolVersionError`: code **`-32022`**, `data.supported` (string array), `data.requested` (string). On HTTP the status **MUST** be `400 Bad Request`.  
  Schema `UnsupportedProtocolVersionError`: https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts
- The client **SHOULD** pick a mutually supported version from `supported` and retry, or surface an error if none exists.
- Servers **MUST** implement `server/discover`. Clients **MAY** call it first; they are not required to. Any RPC may be sent inline.
- Clients and servers **MAY** support multiple versions at once. There is no single session version.

Required per-request `_meta` keys (`RequestMetaObject` in schema.ts; also “Overview” https://modelcontextprotocol.io/specification/2026-07-28/basic):

| Key | Required | Meaning |
| --- | --- | --- |
| `io.modelcontextprotocol/protocolVersion` | **Yes** | Version for this request, e.g. `"2026-07-28"`. |
| `io.modelcontextprotocol/clientCapabilities` | **Yes** | Capabilities for **this** request. `{}` means no optional capabilities. Servers **MUST NOT** infer capabilities from prior requests. |
| `io.modelcontextprotocol/clientInfo` | No | `Implementation` (`name`, `version` required if present). Clients **SHOULD** send it on every request unless configured not to. Servers **SHOULD NOT** branch behavior or security on it. |
| `io.modelcontextprotocol/logLevel` | No | Deprecated (SEP-2577). If absent, server **MUST NOT** emit `notifications/message` for that request. |

Every result **MUST** include `resultType` (`"complete"` or `"input_required"`, or the extension value `"task"`). Clients **MUST** treat a missing `resultType` from an **earlier-protocol** server as `"complete"`. Schema `Result`.

Servers **SHOULD** put `io.modelcontextprotocol/serverInfo` (`Implementation`) on every result `_meta`.

`server/discover` result (`DiscoverResult`, spec “Discovery” https://modelcontextprotocol.io/specification/2026-07-28/server/discover):

- `supportedVersions: string[]`
- `capabilities: ServerCapabilities`
- `instructions?: string` (natural-language guidance; do not duplicate tool descriptions)
- `resultType`, plus cache fields `ttlMs` and `cacheScope` (it is a `CacheableResult`)
- `_meta["io.modelcontextprotocol/serverInfo"]` **SHOULD** be present

Discover is also the stdio **era probe**: a modern client that also speaks legacy **SHOULD** send `server/discover` first. A `DiscoverResult` or a recognized modern error (`UnsupportedProtocolVersionError`) means modern — do not fall back. Any other error or timeout means legacy — fall back to `initialize`. The fallback **MUST NOT** be keyed to one error code.  
stdio, “Backward Compatibility”: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio

A modern-only server that receives `initialize` **SHOULD** name the versions it supports in the error, because legacy clients have no fall-forward. The exact JSON-RPC code for rejecting `initialize` is **implementation-defined** (unknown method, and the request also lacks required `_meta`). Versioning compatibility matrix, “Legacy | Modern”.

#### Legacy (`2025-11-25` and earlier): `initialize` then `initialized`

Lifecycle, “Initialization” and “Version Negotiation”:  
https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle

- Initialization **MUST** be the first interaction.
- Client **MUST** send `initialize` with `protocolVersion` (a version it supports; this **SHOULD** be the latest it supports), `capabilities`, and `clientInfo`.
- If the server supports that version it **MUST** respond with the **same** version. Otherwise it **MUST** respond with another version it supports. This **SHOULD** be the latest the server supports.
- If the client does not support the version in the response, it **SHOULD** disconnect.
- After success the client **MUST** send `notifications/initialized`.
- Client **SHOULD NOT** send requests other than pings before the initialize response. Server **SHOULD NOT** send requests other than pings and logging before `initialized`.
- Both parties **MUST** respect the negotiated version and only use negotiated capabilities.
- HTTP: client **MUST** send `MCP-Protocol-Version` on subsequent requests (added as a MUST in the `2025-06-18` changelog; the `2025-11-25` lifecycle page restates it).

The `2025-11-25` example error for an unsupported version uses code **`-32602`** (Invalid params), `data.supported` / `data.requested`. That is **not** `-32022`. `-32022` exists only in `2026-07-28`.

## 2. Lifecycle and capability objects (`2026-07-28`)

### Lifecycle that replaced initialize / initialized

Changelog “Major changes” items 1–5 and 7–9:  
https://modelcontextprotocol.io/specification/2026-07-28/changelog  
SEP-2575 (stateless): https://modelcontextprotocol.io/seps/2575-stateless-mcp  
SEP-2567 (sessionless handles): https://modelcontextprotocol.io/seps/2567-sessionless-mcp

Removed from the core protocol in this revision:

- `initialize` / `notifications/initialized`
- Protocol sessions and the `Mcp-Session-Id` header
- `ping`
- `logging/setLevel` (replaced by per-request `_meta` log level)
- `notifications/roots/list_changed`
- HTTP GET SSE endpoint and `resources/subscribe` / `resources/unsubscribe` (replaced by `subscriptions/listen`)
- SSE resumability (`Last-Event-ID`, event IDs)
- Server-initiated JSON-RPC requests on the wire. Sampling, elicitation, and roots come back inside an `InputRequiredResult` (multi round-trip), not as standalone server requests.

Operation phase is “any request is legal if it carries `_meta`.” Shutdown is transport-level (close stdin / close HTTP stream). No shutdown RPC.

### `ServerCapabilities` (schema)

Advertised on `server/discover` → `capabilities`. Known keys, not a closed set:

| Key | Shape | Notes |
| --- | --- | --- |
| `tools` | `{ listChanged?: boolean }` | Present if the server offers tools. `listChanged`: will emit `notifications/tools/list_changed`. |
| `resources` | `{ subscribe?: boolean; listChanged?: boolean }` | Readable resources. `subscribe` = per-URI updates. `listChanged` = resource-list notifications. |
| `prompts` | `{ listChanged?: boolean }` | Prompt templates. |
| `completions` | object | Argument autocomplete (`completion/complete`). |
| `logging` | object | **Deprecated** SEP-2577. Structured `notifications/message`. |
| `experimental` | `{ [key: string]: object }` | Non-standard. |
| `extensions` | `{ [extensionId]: object }` | Official/third-party extensions. Keys **MUST** follow `_meta` key rules and **MUST** have a prefix. Empty object = supported, no settings. |

There is **no** top-level `tasks` capability in `2026-07-28`. Tasks moved to `extensions["io.modelcontextprotocol/tasks"]`. There is **no** `instructions` field inside `capabilities`; `instructions` is a sibling of `capabilities` on `DiscoverResult`.

### `ClientCapabilities` (schema)

Declared **per request** at `_meta["io.modelcontextprotocol/clientCapabilities"]`, not once at init:

| Key | Shape | Notes |
| --- | --- | --- |
| `elicitation` | `{ form?: object; url?: object }` | Empty `elicitation: {}` means **form only** (back-compat). |
| `sampling` | `{ context?: object; tools?: object }` | **Deprecated** SEP-2577. `tools` = sampling with tool use. `context` = `includeContext` (itself deprecated for `"thisServer"` / `"allServers"`). |
| `roots` | `{}` | **Deprecated** SEP-2577. |
| `experimental` | map | Non-standard. |
| `extensions` | map | Same key rules as server `extensions`. |

No client `tasks` capability in the core object. Task support is `extensions["io.modelcontextprotocol/tasks"]`.

If one side supports an extension and the other does not, the supporter **MUST** fall back to core behavior or reject the request. Extensions **SHOULD** document the fallback.  
Versioning, “Extension Negotiation”.

### Legacy capability shape (`2025-11-25` initialize), for contrast

https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle

Client: `roots.listChanged`, `sampling`, `elicitation.form` / `elicitation.url`, `tasks.requests.*`, `experimental`.  
Server: `logging`, `prompts.listChanged`, `resources.subscribe` / `resources.listChanged`, `tools.listChanged`, `completions`, `tasks.list` / `tasks.cancel` / `tasks.requests.tools.call`, `experimental`.  
`instructions` and `serverInfo` / `protocolVersion` lived on the **initialize result**, not on `server/discover`.

## 3. Tools (`2026-07-28`)

Spec: https://modelcontextprotocol.io/specification/2026-07-28/server/tools  
Schema interfaces: `ListToolsRequest`, `ListToolsResult`, `CallToolRequest`, `CallToolResult`, `Tool`, `ToolAnnotations`, `ToolListChangedNotification`.

### Capability

Servers that support tools **MUST** declare `tools`.  
Servers that declare `tools` **MUST** answer `tools/list` with the set currently available to the requesting client. The set **MAY** be empty and **MAY** change over time. It **MUST NOT** vary per connection or as a side effect of other requests on the connection. It **MAY** vary by the authorization on the request (scopes are per-request input, not connection state).  
Servers **SHOULD** return tools in a deterministic order when the set has not changed.

`tools: {}` is valid (no `listChanged`). `listChanged: true` means the server will emit list-changed notifications (see below). The tools page example shows `"listChanged": true` inside the capability object; the schema marks `listChanged` optional.

### `tools/list`

`ListToolsRequest` extends `PaginatedRequest`. Params:

- `cursor?: string` — opaque. Only pagination control. **No** `query`, `filter`, `include`, or `exclude` field exists on this request in schema.ts.
- `_meta` — required request metadata (section 2).

`ListToolsResult` extends `PaginatedResult` and `CacheableResult`:

- `resultType`: `"complete"` on a finished list (required on this revision).
- `tools: Tool[]`
- `nextCursor?: string` — present if more pages exist.
- `ttlMs: number` — **required**, `>= 0`.
- `cacheScope: "public" | "private"` — **required**.

### `Tool` object

| Field | Required | Spec / schema |
| --- | --- | --- |
| `name` | Yes | Programmatic id. See name rules below. |
| `title` | No | Human display name. Precedence: `title`, then `annotations.title`, then `name`. |
| `description` | No | Hint to the model. |
| `inputSchema` | Yes | JSON Schema. Root `type` **MUST** be `"object"`. **MUST** be a schema object, not `null`. Defaults to JSON Schema **2020-12** when `$schema` is omitted. Any 2020-12 keyword is allowed (`oneOf` / `anyOf` / `allOf` / `$ref` / `$defs`, not only `properties`). No-parameter tools: `{ "type": "object", "additionalProperties": false }` is the recommended form; `{ "type": "object" }` accepts any object. |
| `outputSchema` | No | JSON Schema 2020-12 for `structuredContent`. **Not** restricted to root `type: "object"` in this revision (arrays are valid). `2025-11-25` schema **was** restricted to root `type: "object"`. |
| `annotations` | No | `ToolAnnotations`. Hints, not guarantees. |
| `icons` | No | `Icon[]`: `src` (https or `data:` URI), optional `mimeType`, `sizes` (`"48x48"` or `"any"`), `theme` (`"light"` \| `"dark"`). |
| `_meta` | No | `MetaObject`. See key rules below. |
| `execution` | **Absent** | Present in `2025-11-25` (`execution.taskSupport`). **Not** a field on `Tool` in `2026-07-28` schema.ts. |

`x-mcp-header` may be set on an `inputSchema` **property** (not on the tool). It names an `Mcp-Param-{name}` HTTP header. Constraints (tools spec, “x-mcp-header”): non-empty, HTTP token, no CR/LF, case-insensitively unique, primitive integer/string/boolean only (not `number`), statically reachable from the schema root. Streamable HTTP clients **MUST** drop a tool whose annotation violates this. Other transports **MAY** ignore it. Servers **SHOULD NOT** mark secrets with `x-mcp-header`.

#### Tool names (SHOULD, not MUST)

SEP-986, restated in the tools spec, “Tool Names”:

- **SHOULD** be 1–128 characters.
- **SHOULD** be case-sensitive.
- **SHOULD** use only `A-Z` `a-z` `0-9` `_` `-` `.`
- **SHOULD NOT** contain spaces, commas, or other special characters.
- **SHOULD** be unique within one server.
- Aggregators **SHOULD** disambiguate collisions (for example prefix with a server identifier). `serverInfo.name` is **not** guaranteed unique and **SHOULD NOT** be used as the disambiguator.

#### `ToolAnnotations` (unchanged set; no new hint keys in this revision)

Schema `ToolAnnotations`. All properties are **hints**. Clients **MUST** treat them as untrusted unless the server is trusted (tools spec callout).

| Field | Default if omitted | Meaning |
| --- | --- | --- |
| `title` | (none; fall back to tool `name`) | Human title. Tool-level `title` wins over this. |
| `readOnlyHint` | `false` | `true` = does not modify its environment. |
| `destructiveHint` | `true` | Meaningful only when `readOnlyHint == false`. `false` = additive updates only. |
| `idempotentHint` | `false` | Meaningful only when not read-only. Same args ⇒ no additional effect. |
| `openWorldHint` | `true` | `true` = may touch an open world (web search). `false` = closed domain (memory tool). |

No other annotation keys are in the `2026-07-28` schema. SEP-3172 (“optional recovery metadata”) was still a **proposal** on the public SEP board as of 2026-10-23 (https://plan.modelcontextprotocol.io/seps) and is **not** in the schema. Do not implement it as if it were spec.

#### `_meta` key rules (tools, content blocks, implementations)

Schema `MetaObject` comment:

- Optional prefix: dot-separated labels, then `/`. Labels start with a letter, end with a letter or digit; interior may include `-`.
- **SHOULD** use reverse DNS (`com.example/…`).
- Any prefix whose **second** label is `modelcontextprotocol` or `mcp` is reserved (`io.modelcontextprotocol/`, `dev.mcp/`). `com.example.mcp/` is not reserved.
- Name segment: starts and ends alphanumeric; interior may include `-` `_` `.`.
- Implementations **MUST NOT** assume meaning for reserved keys beyond what the spec defines.

SEP-414 documents OpenTelemetry keys `traceparent`, `tracestate`, `baggage` on `_meta` (changelog minor change 2).

### `tools/call`

`CallToolRequestParams`:

- `name: string` (required)
- `arguments?: { [key: string]: unknown }`
- plus `InputResponseRequestParams`: optional `inputResponses`, optional `requestState` (opaque; client **must not** interpret it — schema comment on `InputRequiredResult`)
- `_meta`, including optional `progressToken` (`string | number`)

The success result is **either** `CallToolResult` **or** `InputRequiredResult` (schema `CallToolResultResponse`). A tasks-capable server may instead return a task result; that shape is defined by the Tasks **extension**, not by `CallToolResult`. See section 4.

`CallToolResult`:

- `resultType`: `"complete"` for a finished call
- `content: ContentBlock[]` — required for this result type. Blocks:
  - `TextContent` `{ type: "text", text, annotations?, _meta? }`
  - `ImageContent` `{ type: "image", data (base64), mimeType, annotations?, _meta? }`
  - `AudioContent` `{ type: "audio", data, mimeType, annotations?, _meta? }`
  - `ResourceLink` `{ type: "resource_link", uri, name, … }` — not guaranteed to appear in `resources/list`
  - `EmbeddedResource` `{ type: "resource", resource, annotations?, _meta? }` — servers that embed resources **SHOULD** implement the `resources` capability
- `structuredContent?: unknown` — any JSON value (object, array, string, number, boolean, or null) conforming to `outputSchema` if one is defined
- `isError?: boolean` — omitted means **false** (success)
- `_meta?`

`Annotations` on content: `audience?: ("user"|"assistant")[]`, `priority?: number` (0–1), `lastModified?: string` (ISO 8601).

If `outputSchema` is set:

- Servers **MUST** return structured results that conform to it.
- Clients **SHOULD** validate them.
- A tool that returns `structuredContent` **SHOULD** also put the serialized JSON in a `TextContent` block (back-compat). The tools spec says “SHOULD” here.

`InputRequiredResult` (`resultType: "input_required"`):

- At least one of `inputRequests` or `requestState` **MUST** be present.
- `inputRequests` maps server-chosen keys to `sampling/createMessage`, `roots/list`, or `elicitation/create` request objects (no JSON-RPC `id` on those inner requests; the map key is the correlator).
- Client retries the **original** method with a **new** JSON-RPC `id` (the id **MUST** differ), same `name` / `arguments`, plus `inputResponses` keyed like `inputRequests`, plus `requestState` if the server sent one.
- These interim results are **not** cacheable.

#### Errors

Tools spec, “Error Handling”:

1. **Protocol errors** (JSON-RPC `error`, models are unlikely to fix these): unknown tool, request that fails `CallToolRequest` schema, server faults. Unknown tool example uses **`-32602`**. Schema `InvalidParamsError` lists “Unknown tool name or invalid tool arguments” under `-32602`.
2. **Tool execution errors** (actionable): API failures, **input validation** (SEP-1303), business logic. Report **inside** the result with `isError: true` and a text explanation. **SHOULD NOT** be a protocol error, or the model cannot see them.
   - Clients **SHOULD** pass tool execution errors to the model.
   - Clients **MAY** pass protocol errors to the model.

Security, servers **MUST**: validate all tool inputs; access-control them; rate-limit invocations; sanitize outputs.

### `notifications/tools/list_changed` and `tools.listChanged`

Schema: method `"notifications/tools/list_changed"`. Optional `params`. Delivered **only** on a `subscriptions/listen` stream whose filter set `toolsListChanged: true`.

Tools spec, “List Changed Notification”: servers that declared `listChanged` **SHOULD** send this notification to clients that opened such a stream.

This is a behavior change from `2025-06-18` schema text, which said the notification “may be issued by servers without any previous subscription from the client.”  
https://modelcontextprotocol.io/specification/2025-06-18/schema (`ToolListChangedNotification`)

`subscriptions/listen` (https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions):

- Client sends `notifications: { toolsListChanged?: boolean, promptsListChanged?: boolean, resourcesListChanged?: boolean, resourceSubscriptions?: string[] }`.
- Server **MUST NOT** send types the client did not request.
- Server **MUST** send `notifications/subscriptions/acknowledged` first, with `_meta["io.modelcontextprotocol/subscriptionId"]` equal to the listen request id, and **MUST NOT** send subscription notifications before that ack. The ack’s `notifications` object is the subset the server will honor.
- Every notification on the stream **MUST** carry that `subscriptionId`. On stdio, clients **MUST** demux with it.
- Client **SHOULD** compare the ack filter to what it requested.
- On stdio, reconnect **MUST** re-send `subscriptions/listen` (no subscription state across connections).
- Request-scoped notifications (`notifications/progress`, `notifications/message`) stay on the **request’s** response stream, not on the listen stream (changelog major change 4).

### Server-side tool search: not in the spec

Checked `schema/2026-07-28/schema.ts` `ClientRequest` union. Client methods are only:

`server/discover`, `completion/complete`, `prompts/get`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`, `subscriptions/listen`, `tools/call`, `tools/list`.

There is **no** `tools/search`, no list filter, no include/exclude, and no lazy-load RPC. `tools/list` reduction is **pagination only** (`cursor` / `nextCursor`). The Progressive Disclosure working group exists (https://modelcontextprotocol.io/community/working-groups/progressive-disclosure) and has not added a server search method to this revision.

What the official docs actually tell **clients** to do (not a server requirement):

https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices — “Progressive Tool Discovery”

- Host still fetches definitions with `tools/list`.
- Host **defers** putting them in the model context.
- Host exposes its **own** meta-tools (`search_tools`, then `get_tool_details`). Those names are a client pattern, not protocol methods.
- Suggested retrieval: keyword (BM25/regex), embeddings, a small subagent, or hybrid. Provider-native tool search (the page names OpenAI and Anthropic) may be used instead of a custom index.
- Threshold guidance on that page: switch when tool definitions are a large share of context; the page suggests implementing a threshold around 1–5% of the window. That number is docs guidance, not a protocol MUST.
- Cache definitions host-side. Re-index when `notifications/tools/list_changed` arrives. Treat a cached list as stale on that notification even if `ttlMs` has not expired (same rule as the caching spec).
- Group tools by server. Do not reshuffle the model’s `tools` array mid-conversation if that blows the provider prompt cache; append, or route through a stable `call_tool` meta-tool.

Server cards explicitly **omit** tool lists. A static card cannot be the tool catalog. SEP-2127, “Why Exclude Primitives?”: https://modelcontextprotocol.io/seps/2127-mcp-server-cards

### Can a tool declare that it returns tasks?

**Not in `2026-07-28` core.** `Tool.execution.taskSupport` was a `2025-11-25` field (`"forbidden"` default, `"optional"`, `"required"`) and is gone from the current `Tool` interface.

`2025-11-25` rules (for dual-era implementations only): https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks and https://modelcontextprotocol.io/specification/2025-11-25/server/tools

- If the server did not advertise `tasks.requests.tools.call`, clients **MUST NOT** task-augment, regardless of `execution.taskSupport`.
- `"forbidden"` or absent: clients **MUST NOT** invoke as a task (default). Servers **SHOULD** return `-32601` if the client does.
- `"optional"`: client **MAY** do either.
- `"required"`: client **MUST** invoke as a task; server **MUST** return `-32601` if it does not.

`2026-07-28` replacement: the client opts into the Tasks **extension** on the request. The server decides per call whether to return a task handle. There is no per-tool `taskSupport` flag in the core schema. Details in section 4.

## 4. Features since `2025-06-18` that a coding-agent server cares about

Baseline for “since 2025-06-18” is that revision’s changelog plus the `2025-11-25` and `2026-07-28` changelogs.

### Tasks

**`2025-11-25` (experimental, in core).** SEP-1686. Methods: `tasks/get` (poll), `tasks/result` (blocks until terminal), `tasks/list` (paginated), `tasks/cancel`, notification `notifications/tasks/status`. Capability `tasks` on initialize. Tool opt-in via `execution.taskSupport`. Statuses include `working`, `input_required`, `completed`, `failed`, `cancelled`. Requestors **MUST NOT** rely on the status notification.

**`2026-07-28` (official extension, not core).** Changelog major change 6. SEP-2663. Overview: https://modelcontextprotocol.io/extensions/tasks/overview  
Full normative text lives in the `modelcontextprotocol/ext-tasks` repository (the overview says so). The overview is the official summary used here:

- Identifier: `io.modelcontextprotocol/tasks` in `extensions` on both sides.
- Client declares it on **each** request’s `clientCapabilities.extensions`. Server advertises it on `server/discover`.
- Server **MUST NOT** return a task to a client that did not declare the extension (overview: “Never return a task to a client that did not declare support”).
- Response is a `CreateTaskResult` with `resultType: "task"`, a `taskId`, status, TTL, and `pollIntervalMs`. The task is durable **before** the response is sent.
- Methods named by the overview: `tasks/get` (poll; terminal states include `result` or `error`), `tasks/update` (client supplies `inputResponses` when status is `input_required`), `tasks/cancel` (cooperative; server acks, not obligated to stop).
- **Removed relative to `2025-11-25`:** `tasks/result` (blocking), `tasks/list`. Servers may return a task **unsolicited** (no per-request task flag, no per-tool `taskSupport`).
- Optional push: `notifications/tasks` on `subscriptions/listen`. Polling is the default. Overview says clients that have notifications can rely on them instead of polling. (The `2025-11-25` core spec said the opposite: requestors MUST NOT rely on `notifications/tasks/status`. Do not mix the two revisions.)
- Statuses: `working`, `input_required`, `completed`, `failed`, `cancelled`. Terminal: completed / failed / cancelled.
- A tools-only core server that does not advertise the extension never returns `resultType: "task"`. Long work is either a blocking `tools/call` (with optional `notifications/progress`) or an explicit handle passed as an ordinary tool argument (SEP-2567, tools spec “Stateful Tools” — that section is **non-normative**; the protocol has no handle type).

### Elicitation (form + URL)

Spec: https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation

- Form mode: in the `2025-06-18` changelog (PR #382). URL mode: added `2025-11-25` (SEP-1036).
- `2026-07-28`: elicitation is an inner request on `InputRequiredResult.inputRequests`, method `elicitation/create`. The `2025-11-25` notification `notifications/elicitation/complete` and the URL-mode `elicitationId` field are **removed** (changelog minor change 11). Correlation goes in `requestState`.
- Client **MUST** declare `elicitation` and **MUST** support at least one of `form` or `url`. `elicitation: {}` ≡ form only. Servers **MUST NOT** request a mode the client did not declare. Missing capability → `-32021` `MissingRequiredClientCapabilityError` (schema example is the elicitation case). HTTP status `400`.
- Form: `mode` omitted or `"form"`, `message`, `requestedSchema` (flat object, primitives only: string / number / integer / boolean / enum). String formats: `email`, `uri`, `date`, `date-time`. Defaults allowed (SEP-1034). Enums: untitled `enum`, titled `oneOf`/`const`+`title`, multi-select arrays; legacy `enumNames` still in the schema union.
- URL: `mode: "url"` required, `message`, `url` **MUST** be a valid URL. For secrets, payments, and credential-granting flows. Servers **MUST NOT** use form mode for secrets/credentials. URL mode is not the MCP OAuth flow.
- Result `ElicitResult.action`: `"accept"` | `"decline"` | `"cancel"`. `content` only when accept + form mode.

### Logging, progress, cancellation

**Logging — deprecated** (SEP-2577). Spec: https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/logging

- Capability `logging`.
- `logging/setLevel` is **removed**. Client opts in with `_meta["io.modelcontextprotocol/logLevel"]` on a request. If absent, server **MUST NOT** emit `notifications/message` for that request.
- Levels (RFC 5424): `debug`, `info`, `notice`, `warning`, `error`, `critical`, `alert`, `emergency`.
- Notification `notifications/message`: `level`, optional `logger`, `data`.
- Suggested migration: stderr on stdio, or OpenTelemetry. stdio servers **MAY** write UTF-8 logs to stderr; clients **SHOULD NOT** treat stderr as an error signal.  
  https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio

**Progress** — still core, optional. https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/progress

- Client puts `progressToken` (`string | number`) in request `_meta`. Token **MUST** be unique across active requests.
- Server **MAY** send `notifications/progress` on that request’s stream: `progress` **MUST** increase each time; `total` optional; `message` **SHOULD** be human-readable. `progress` / `total` **MAY** be floats. (`message` was added in `2025-03-26`.)
- Notifications **MUST** stop after completion. Receiver is not obligated to send any.

**Cancellation.** https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation

- Client **SHOULD** cancel work it no longer wants.
- **stdio:** client **MUST** send `notifications/cancelled` with `requestId` and optional `reason`. Server **SHOULD** stop and **MUST NOT** send further messages for that request (stdio page). Cancellation page: servers **SHOULD** stop, free resources, and not respond; they **MAY** ignore unknown, finished, or uncancellable requests.
- **Streamable HTTP:** closing the SSE response stream **is** cancellation. Server **MUST** treat client disconnect as cancel. Do **not** POST `notifications/cancelled`. This revision defines no client-to-server notification POST for the core protocol.
- Server-sent `notifications/cancelled` **MUST** only reference a `subscriptions/listen` id (tear down that stream). Servers **MUST NOT** use it to cancel anything else.
- Implementations **SHOULD** time out requests. **MAY** reset the timeout on progress. **SHOULD** still enforce a maximum timeout.

`ping` is removed (changelog major change 5). A `2026-07-28`-only server does not implement it.

- `icons`: `2025-11-25` (SEP-973). Clients that render icons **MUST** support `image/png` and `image/jpeg`/`image/jpg`, and **SHOULD** support `image/svg+xml` and `image/webp` (schema `Icons`).
- `Implementation` optional `description` and `websiteUrl`: description added `2025-11-25` to align with registry `server.json`.

- `outputSchema` + `structuredContent`: `2025-06-18` (PR #371). `2026-07-28` (SEP-2106) allows any JSON Schema 2020-12 keywords and any JSON value in `structuredContent`, plus `$ref` resolution bounds. https://modelcontextprotocol.io/seps/2106-json-schema-2020-12

### Server cards, `.well-known`, MCP registry

These are **not** core protocol requirements for a `2026-07-28` server.

- **Server cards** are an Extensions Track SEP, Final, optional. https://modelcontextprotocol.io/seps/2127-mcp-server-cards  
  Normative schema is in `modelcontextprotocol/experimental-ext-server-card`, not in `schema/2026-07-28/schema.ts`.  
  Cards are static HTTP metadata (identity, remote endpoints, protocol versions). They **do not** list tools, resources, prompts, capabilities, or extensions.  
  Recommended card location named by the SEP: `` /server-card `` (any unreserved URI is allowed). Domain catalog: `/.well-known/ai-catalog.json`.  
  **Not** in the SEP text fetched for this note: a required `/.well-known/mcp.json`. If you see that path in a blog, it is not this SEP’s discovery path.
- If a card and `server/discover` disagree, clients **SHOULD** prefer live `server/discover`.
- **MCP Registry** is a separate publishing catalog (`server.json` for packages and remotes). Docs: https://modelcontextprotocol.io/registry/about  
  It is not an RPC and not required to speak the protocol. SEP-2127: registry and server cards are different documents; the registry schema is owned by the registry.
- **OAuth** protected-resource metadata uses a different well-known path: `/.well-known/oauth-protected-resource` (RFC 9728), only when the HTTP server requires authorization. https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery

### Transports and auth (localhost JSON)

Transports overview: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports

The spec does **not** require stdio or HTTP. It defines two standard bindings and allows others:

1. **stdio** — client-spawned process, newline-delimited JSON-RPC, no embedded newlines, stdout is MCP-only. https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio
2. **Streamable HTTP** — one POST endpoint; response is either `application/json` or a request-scoped `text/event-stream`. Introduced `2025-03-26`. `2026-07-28` removes the GET stream, `Mcp-Session-Id`, and `Last-Event-ID`. https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http
3. **Custom transports MAY** be implemented. They **MUST** keep JSON-RPC, the message patterns (servers do not send JSON-RPC requests; clients do not send JSON-RPC responses), and per-request `_meta`. A custom transport over a reliable bidirectional byte stream (Unix socket, TCP) **SHOULD** reuse stdio framing (one JSON-RPC message per line). Only process-lifecycle rules are stdio-specific.

HTTP+SSE (`2024-11-05`) has been deprecated since `2025-03-26` and is classified Deprecated (SEP-2596). New implementations **SHOULD NOT** adopt it.

Streamable HTTP requirements that **do not** apply to a non-HTTP socket:

- Single POST endpoint; client **MUST** send `Accept: application/json, text/event-stream`.
- **MUST** send `MCP-Protocol-Version`, `Mcp-Method` (all requests), and `Mcp-Name` for `tools/call`, `resources/read`, and `prompts/get` (`params.name` or `params.uri`).
- Header/body mismatch or missing required header: HTTP `400`, JSON-RPC `-32020`.
- Unknown RPC method: HTTP `404` **and** JSON-RPC `-32601`.
- Unsupported version: HTTP `400` and `-32022`.
- Notification POST that is accepted: HTTP `202` empty body. (Core protocol defines no client notification POST on this transport.)
- `Origin`, if present and invalid: HTTP `403`.
- Local HTTP servers **SHOULD** bind `127.0.0.1`, not `0.0.0.0`, and **SHOULD** authenticate connections (DNS-rebinding note).
- JSON-RPC **batching is not** part of the protocol (removed `2025-06-18`). One message per POST / per stdio line.

**Authorization is OPTIONAL.** https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization

- HTTP implementations that support it **SHOULD** conform: MCP server is an OAuth 2.1 resource server; client sends `Authorization: Bearer` on every HTTP request; tokens **MUST NOT** be in the query string.
- STDIO implementations **SHOULD NOT** follow that OAuth spec; credentials **SHOULD** come from the environment.
- Alternative transports **MUST** follow established security practice for that protocol. The spec does not define an OAuth handshake for a raw localhost JSON socket.
- `2026-07-28` auth deltas (only if you implement HTTP OAuth): `iss` in authorization responses **SHOULD** be sent (RFC 9207) and clients **MUST** validate a present `iss` (SEP-2468); Dynamic Client Registration is **deprecated** in favor of Client ID Metadata Documents but remains for backwards compatibility; credentials are bound to the issuing authorization server (SEP-2352).

### JSON-RPC error codes the spec reserves

Schema comment “MCP error codes” and the consts in schema.ts. JSON-RPC 2.0 reserves `-32000`…`-32099` for server errors. MCP splits that range:

| Code | Name | When |
| --- | --- | --- |
| `-32700` | Parse error | Invalid JSON. |
| `-32600` | Invalid request | Not a valid JSON-RPC request. |
| `-32601` | Method not found | Unknown method, or method gated on a capability the server did not advertise (example: `prompts/list` without `prompts`). On Streamable HTTP, also HTTP `404`. |
| `-32602` | Invalid params | Unknown tool, bad tool arguments, unknown prompt, bad/expired cursor, bad log level, elicitation mode not in client capabilities, sampling tool-result shape errors. Also the **new** code for resource-not-found (`2026-07-28` moved it off `-32002`). |
| `-32603` | Internal error | Unexpected failure. |
| `-32000` … `-32019` | Implementation-defined | Spec will never assign these. Receivers **MUST NOT** invent cross-implementation meaning. Existing SDK usage is grandfathered. |
| `-32020` | `HeaderMismatch` | HTTP headers ≠ body, or required headers missing/malformed. HTTP `400`. |
| `-32021` | `MissingRequiredClientCapability` | `data.requiredCapabilities`. HTTP `400`. |
| `-32022` | `UnsupportedProtocolVersion` | `data.supported`, `data.requested`. HTTP `400`. |
| `-32023` … `-32099` | Reserved for future MCP codes | Allocated sequentially from `-32020` upward. |

Retired, never reused:

- `-32002` — resource not found in `2025-11-25` and earlier (now `-32602`).
- `-32042` — “URL elicitation required”, `2025-11-25` only.

`error.message` **SHOULD** be one concise sentence. `error.data` is sender-defined except where the schema types it (`supported`/`requested`, `requiredCapabilities`).

### Pagination

https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/pagination

- Opaque cursor, not page numbers. `Cursor` is a string.
- Page size is server-chosen. Clients **MUST NOT** assume a fixed page size.
- Clients **MUST** treat cursors as opaque: do not parse, modify, or treat `""` as end-of-list. A missing `nextCursor` is end-of-list (client **SHOULD** treat it that way).
- Operations: `resources/list`, `resources/templates/list`, `prompts/list`, `tools/list`.
- Servers **SHOULD** provide stable cursors and handle invalid cursors gracefully. Invalid cursor **SHOULD** be `-32602`.
- Clients **SHOULD** support both paginated and non-paginated flows.
- Caching interaction: each page has its own `ttlMs`. Same `cacheScope` on every page of one list (**MUST**). No cross-page consistency. Clients that need a snapshot **SHOULD** re-fetch from the start (no cursor). A cursor error **SHOULD** drop all cached pages and restart.

### Caching (new in `2026-07-28`, SEP-2549)

https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching

Servers **MUST** include `ttlMs` (`>= 0`) and `cacheScope` on `resultType: "complete"` results of: `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`.

- `ttlMs == 0`: immediately stale. Client **MAY** re-fetch whenever it needs the data.
- Positive: client **SHOULD** treat as fresh for that many milliseconds after receipt.
- Absent (old servers only): client **SHOULD** assume `0`.
- Negative: client **SHOULD** treat as `0`.
- TTL is a hint, not a promise. Servers **MAY** change data before expiry.
- Clients **SHOULD NOT** use TTL as a background poll interval.
- `list_changed` while fresh: cache **should** be treated as immediately stale (caching spec prose; the RFC 2119 word on that sentence is lowercase “should”).
- `"public"` may be shared across callers. `"private"` **MUST NOT** be shared across authorization contexts.
- `cacheScope: "public"` on an authenticated `tools/list` may be reused for other tokens. Servers **MUST NOT** rely on `cacheScope` as the access-control mechanism.
- Results of MRTR retries (`inputResponses` or `requestState` present) **MUST NOT** be cached.

## 5. Client behavior when tools change

### What the spec requires of a conformant client

The spec does **not** say the client **MUST** call `tools/list` again. It says:

- Servers with `tools.listChanged` **SHOULD** emit `notifications/tools/list_changed` on listen streams that opted in (tools spec).
- Receiving that notification invalidates a fresh cache entry; the client should treat it as immediately stale (caching spec, “Interaction with Notifications”). The sequence diagram then shows the client calling `tools/list`.
- Clients **MAY** re-fetch before TTL if a later call fails in a way that suggests the tool is gone (caching spec).
- Clients **SHOULD** re-fetch a stale entry on next access, not on a timer.
- To receive the notification at all on `2026-07-28`, the client must open `subscriptions/listen` with `toolsListChanged: true` and wait for the ack. A client that never listens will not see list changes until TTL expiry or an error.

`2025-11-25` / `2025-06-18` sequence diagrams show the same client re-list step, and those revisions allowed the notification **without** a prior subscribe.

### Official SDK guidance (coding agents refreshing mid-session)

**TypeScript SDK (official docs, v2):**

- https://ts.sdk.modelcontextprotocol.io/v2/clients/subscriptions.html — On a `2026-07-28` connection, change notifications arrive only on a `subscriptions/listen` stream. Nothing arrives unsolicited. `client.listen({ toolsListChanged: true })` then `setNotificationHandler('notifications/tools/list_changed', …)` which calls `listTools()`.
- `Client` option `listChanged.tools.onChanged` opens that stream after connect (intersection of the option and the server’s `tools.listChanged`) and re-fetches with cache bypass. A later manual `setNotificationHandler` for the same method replaces it.
- Server side: https://ts.sdk.modelcontextprotocol.io/v2/servers/notifications — `sendToolListChanged()`; high-level `registerTool` / `update` / `disable` / `remove` send it automatically. `McpServer` advertises `tools.listChanged: true` once a tool is registered. Low-level `Server` throws if you send the notification without the capability.
- Source comment in `packages/client/src/client/client.ts` (main): list-changed evicts `tools/list`, and the auto-refresh uses `cacheMode: 'refresh'` so a broken cache `delete` cannot keep serving the stale entry. https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/client/src/client/client.ts

**Python SDK (official repo source, not a README policy statement):**

- `src/mcp/client/caching.py` at commit `1963af52`: `ToolListChangedNotification` evicts `tools/list`. The next `list_tools` hits the wire. The cache does not itself re-list. https://github.com/modelcontextprotocol/python-sdk/blob/1963af52/src/mcp/client/caching.py
- Test `test_a_tools_list_changed_notification_makes_the_next_list_refetch` documents that as the spec’s cache-invalidation behavior, and notes the in-process **modern** path “drops standalone server notifications,” so the test uses `mode="legacy"`. https://github.com/modelcontextprotocol/python-sdk/blob/1963af52/tests/client/test_client_caching.py
- v1.x snippet `send_tool_list_changed()` after a dynamic register: https://github.com/modelcontextprotocol/python-sdk/blob/v1.x/examples/snippets/servers/tool_change_notifications.py
- Issue #2107 (opened 2026-02-19, still labeled open in the fetched issue page) said the then-current client **dropped** list-changed notifications. That issue describes older client code. The caching eviction above is later source. Do not treat #2107 as the current SDK contract without re-reading `session.py` at the commit you ship.

Host guidance that **is** written for coding agents is the client best-practices page (section 3): refresh the search index on `list_changed`; do not assume the model’s tool array updates itself.

### Cursor, Claude, Codex

No first-party spec, SEP, or SDK README fetched for this note states whether Cursor, Claude, or Codex refresh tools on `notifications/tools/list_changed`. The official extension matrix lists Cursor and Claude for **extensions**, not for list-changed. Omitted rather than guessed.

## 6. Checklist: tools-only server, `protocolVersion: "2026-07-28"`

Assumed surface: `server/discover`, `tools/list`, `tools/call`. No resources, prompts, completions, logging, sampling, roots, elicitation, tasks, or HTTP OAuth. Transport may be a custom localhost JSON socket that follows the custom-transport rules (stdio framing if it is a reliable byte stream).

### MUST

1. Speak JSON-RPC 2.0, UTF-8. One message per framing unit. Do not batch.
2. Implement `server/discover`. Return `supportedVersions` including `"2026-07-28"`, `capabilities` (at least `tools`), `resultType: "complete"`, `ttlMs >= 0`, `cacheScope`.
3. On every result, include `resultType`.
4. Reject a requested version you do not implement with `-32022`, `data.supported` and `data.requested`. Do not pretend `initialize` negotiated it.
5. Do not require `initialize` / `notifications/initialized` for modern clients. Do not keep protocol session state that makes `tools/list` differ per connection.
6. If you declare `tools`, answer `tools/list` with the tools available to **this** request’s caller. Empty is legal. The list **MUST NOT** change as a side effect of another request on the same connection.
7. `tools/list` pages: `tools` array, optional `nextCursor`, required `ttlMs` and `cacheScope`. Same `cacheScope` on every page. Do not cache or serve a page for a different cursor.
8. Each tool: `name`, `inputSchema` with root `type: "object"` (a real schema, not null). Honor `outputSchema` if you set it: `structuredContent` **MUST** conform.
9. `tools/call`: on success return `content` (array of content blocks) and `resultType: "complete"`, or an `InputRequiredResult` if you actually need MRTR (a tools-only server that does not elicit/sample should not).
10. Unknown tool name and malformed `tools/call` params: JSON-RPC `-32602`, not `isError`.
11. Input-validation and tool-business failures: result with `isError: true` and a text `content` block, not a protocol error.
12. Validate tool inputs, enforce access control, rate-limit calls, sanitize outputs (tools spec security list).
13. Methods you do not implement (`prompts/list`, `resources/list`, `ping`, `logging/setLevel`, `resources/subscribe`, …): `-32601`. On Streamable HTTP that is also HTTP 404; on a custom socket, JSON-RPC only.
14. If the client omits a capability you need for a request you chose to accept: `-32021` with `data.requiredCapabilities`. Do not infer capabilities from an earlier request.
15. Do not send `notifications/tools/list_changed` except on a `subscriptions/listen` stream that set `toolsListChanged: true`, and not before `notifications/subscriptions/acknowledged` with `subscriptionId`.
16. If you implement listen: ack first; only echo filters you will honor; tag every notification with `io.modelcontextprotocol/subscriptionId`.
17. Cursors are opaque. Invalid cursor **SHOULD** be `-32602` (see SHOULD). Do not require the client to understand cursor format.
18. `_meta` keys you emit under a reserved `modelcontextprotocol` / `mcp` second label must be spec-defined keys only (`serverInfo`, `subscriptionId`, and the documented OTel keys if you use them).
19. Custom byte-stream transport: preserve JSON-RPC and the “server does not send JSON-RPC requests” rule. **SHOULD** use newline framing (one message per line, no embedded newlines) — the SHOULD is on the transport overview; stdio itself **MUST NOT** embed newlines.
20. Do not write non-MCP bytes on the MCP channel (stdio: stdout is MCP-only; logs go to stderr).

### SHOULD

1. Include `io.modelcontextprotocol/serverInfo` (`name`, `version`) on every result `_meta`.
2. Return `tools/list` in a stable order when the set is unchanged.
3. If the tool list changes and you set `tools.listChanged: true`, emit `notifications/tools/list_changed` to opted-in listeners. If the list never changes, omit `listChanged` or set it `false` and do not implement listen.
4. Tool names: 1–128 chars, case-sensitive, charset `A-Za-z0-9_.-`, unique on this server.
5. If you return `structuredContent`, also return the same JSON as a text content block.
6. Stable cursors; `-32602` on a bad cursor.
7. `error.message` is one sentence.
8. `ttlMs` reflects how long the catalog can stay fresh. Use `0` if clients must re-list every time. Use `"private"` if the tool list depends on the caller.
9. Time out your own outbound work. On stdio, stop when you see `notifications/cancelled` for that id. On HTTP, treat a closed response stream as cancel.
10. If you accept `progressToken`, only emit `notifications/progress` for that token, with increasing `progress`, and stop when the call finishes.
11. For cross-call state, return an explicit id in the tool result and take it as a normal argument later. Do not invent a session header. State the handle’s lifetime in the tool description. Expired handle → `isError: true`, not a silent success (tools spec “Stateful Tools”; that section is non-normative guidance).
12. Do not put secrets in `x-mcp-header` properties.
13. If a legacy client sends `initialize` and you are modern-only, say which versions you support in the error text.
14. Bind a local HTTP port to `127.0.0.1` if you ever speak Streamable HTTP. Do not implement the OAuth spec on a raw socket; auth is optional and HTTP-shaped.
15. Human-in-the-loop confirmation is a **client** SHOULD, not a server wire requirement.

### Not required for this profile

`initialize`, `ping`, resources, prompts, completions, logging, sampling, roots, elicitation, Tasks extension, icons, annotations, `outputSchema`, `title`, `subscriptions/listen` (unless `listChanged` is true), server cards, registry `server.json`, OAuth, `Mcp-Session-Id`, SSE event ids.

## 7. Ten deltas versus initialize + `tools/list` + `tools/call` on `2025-03-26` or `2025-06-18`

A server that only did the old handshake and the two tool methods is missing all of the following on `2026-07-28`:

1. **`initialize` / `notifications/initialized` are gone.** Version and client capabilities ride on every request’s `_meta`. Unsupported version is `-32022` with `data.supported`, not a session-long choice and not the legacy `-32602` example.
2. **`server/discover` is mandatory**, with `supportedVersions`, `capabilities`, `resultType`, `ttlMs`, `cacheScope`.
3. **Every result needs `resultType`.** `tools/list` and discover also need `ttlMs` and `cacheScope`. List order **SHOULD** be stable because clients cache it.
4. **`tools/list` must not vary per connection** or as a side effect of other calls. Dynamic catalogs notify through `subscriptions/listen`, not an unsolicited `list_changed` on the connection.
5. **No server-side tool search.** Pagination is the only protocol filter. Search/lazy-load is a client pattern (`search_tools` in the host), not an RPC you implement.
6. **`tools/call` can return `input_required`** (MRTR) instead of a final `CallToolResult`. Servers no longer emit JSON-RPC requests of their own. `ping` is gone.
7. **Tool schemas are JSON Schema 2020-12** unless `$schema` says otherwise, and `structuredContent` may be any JSON value. `outputSchema` conformance is a MUST when you declare it (`2025-06-18` added the fields; `2025-03-26` did not have them).
8. **`execution.taskSupport` is not how async works** (`2025-11-25` only). In `2026-07-28`, async is the Tasks extension (`resultType: "task"`, `tasks/get` / `tasks/update` / `tasks/cancel`) and only if the client declared `io.modelcontextprotocol/tasks`. Otherwise block, use progress notifications, or pass an ordinary handle argument.
9. **Annotations are the same four hints** (`readOnlyHint` default false, `destructiveHint` default true, `idempotentHint` default false, `openWorldHint` default true) plus optional `title`. They are untrusted hints. No new annotation keys landed in the schema.
10. **Error-code split and transport.** `-32020`/`-32021`/`-32022` are spec-reserved; `-32002` and `-32042` are retired. Unknown methods are `-32601`. Tool failures the model can fix use `isError: true`. HTTP gained `Mcp-Method` / `Mcp-Name` and lost sessions; a localhost socket is a **custom transport** (stdio framing recommended) and **SHOULD NOT** grow an OAuth layer. Server cards and the registry are optional and out of band.
