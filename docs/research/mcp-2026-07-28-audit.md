# MCP 2026-07-28 audit of tm-control-mcp

Date: 2026-10-23. Spec facts are from the Model Context Protocol revision
`2026-07-28` (previous revision `2025-11-25`). Implementation facts are from
this repo's socket and tool-pack code. Clause-level spec notes, with URLs,
are in [mcp-2026-07-28-spec.md](mcp-2026-07-28-spec.md).

## Verdict

`2026-07-28` is the current spec revision. This plugin is a localhost JSON
tool bridge with a live pack registry. It is not an MCP server. A coding
agent that speaks MCP cannot connect to `127.0.0.1:30006`, and a pack
registration does not notify any agent.

Dynamic catalog updates already work inside the plugin. The missing piece is
a process that speaks MCP and turns that version bump into
`notifications/tools/list_changed` on a client-opened
`subscriptions/listen` stream. Tool search is a host feature in the current
docs, not a server RPC.

## What the spec requires for tools

Sources:

- Changelog: https://modelcontextprotocol.io/specification/2026-07-28/changelog
- Tools: https://modelcontextprotocol.io/specification/2026-07-28/server/tools
- Discovery: https://modelcontextprotocol.io/specification/2026-07-28/server/discover
- Subscriptions: https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions
- Versioning: https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning
- stdio: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio
- Client best practices: https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices
- TypeScript SDK subscriptions: https://ts.sdk.modelcontextprotocol.io/v2/clients/subscriptions.html

Major breaks from `2025-11-25` and earlier:

1. No `initialize` / `notifications/initialized` handshake. Every request
   carries `io.modelcontextprotocol/protocolVersion` and
   `io.modelcontextprotocol/clientCapabilities` in `_meta`.
2. Servers must implement `server/discover` (supported versions, capabilities,
   identity, optional `instructions`, `ttlMs`, `cacheScope`).
3. List-change notifications are opt-in. The client opens
   `subscriptions/listen` with `toolsListChanged: true`. The server must ack
   with `notifications/subscriptions/acknowledged` and a `subscriptionId`
   before any notification, and must not emit types the client did not
   request. Unsolicited `notifications/tools/list_changed` on the main
   connection is gone.
4. Results require `resultType`: `"complete"`, `"input_required"`, or the
   Tasks-extension value `"task"`. `tools/list` also requires `ttlMs` and
   `cacheScope` (`"public"` or `"private"`). A `list_changed` notification
   invalidates that cache even if the TTL has not expired.
5. The tool list must not vary per connection or as a side effect of other
   requests. Order should stay stable while the set is unchanged, so hosts
   can cache the prompt prefix.
6. Tasks left the core protocol. `Tool.execution.taskSupport` is gone. The
   extension `io.modelcontextprotocol/tasks` returns `resultType: "task"`
   and is polled with `tasks/get`. The server must not return a task unless
   that request's client capabilities declare the extension. Otherwise the
   call blocks, reports progress, or returns an ordinary handle argument.
7. Server-initiated `elicitation/create`, `sampling/createMessage`, and
   `roots/list` were replaced by Multi Round-Trip Requests: a result with
   `resultType: "input_required"`. Roots, sampling, and logging are deprecated
   (SEP-2577). New servers should not add them.

There is no `tools/search` method. Official client guidance puts progressive
discovery in the host: keep `tools/list` out of the model context, expose a
host meta-tool such as `search_tools`, then load one schema with something
like `get_tool_details`. On `notifications/tools/list_changed`, the host
re-indexes that catalog. Provider-native tool search (Anthropic, OpenAI) is
called out as preferable when the host already has it.

Tool annotations are hints, defaulting to the cautious side: `readOnlyHint`
false, `destructiveHint` true, `idempotentHint` false, `openWorldHint` true.
A client that trusts those defaults will treat every unannotated tool as
destructive.

## What this repo actually is

`README.md` and `src/Protocol.as`: one newline-terminated JSON object per TCP
connection on `127.0.0.1:30006`, then the socket closes.

| Request | Response shape |
|---|---|
| `{"route":"status"}` | `{ok, id, route, error, data}` with alive/port/plugin version. No protocol version, no capabilities, no tool-list generation. |
| `{"route":"tools"}` | `data` is an array of `{name, description, input_schema}` plus `{pack}` on pack tools. |
| `{"route":"call","tool":"…","input":{}}` | `data.tool` and `data.result` of `{success, output}` or `{success:false, error, code, …}`. |

Field name is `input_schema` (Anthropic Messages style), not MCP `inputSchema`.
There is no JSON-RPC envelope, no `_meta`, no `resultType`, no
`structuredContent`, no `isError`, no pagination cursor, no `ttlMs`.

Built-in tools are a static list in `BuildToolList()` (`src/McpTools.as`).
README counts 104 release tools, plus DEV-only tools. Pack tools are appended
by `AppendPackTools` (`src/ToolPacks.as`).

## Dynamic packs, as implemented

`RegisterToolPack` / `UnregisterToolPack` / dead-pack sweep call
`InvalidateToolList()`, which increments `g_ToolListVersion`. The next
`GetToolList()` rebuilds and includes `packId.FuncName` entries. Schemas are
inserted into and removed from the input validator at registration time
(`RegisterToolSchema` / `UnregisterToolSchema`).

That is a correct in-process catalog. It does not cross the socket as an
event:

- `g_ToolListVersion` is not on the `status` route.
- Each client connection is one request. There is no stream to write
  `notifications/tools/list_changed` onto.
- `tools/call.py` and any agent using it must ask for `route:tools` or
  `ListToolPacks` again. A session that snapshotted the list at start keeps
  the old set.

Tool names already match the spec's recommended charset (ASCII letters,
digits, `_`, `-`, `.`). Pack ids are prefixed and tool names must not contain
a dot, so public names look like `Visual.Ping`. Order is insertion order for
builtins, then registration order for packs. That satisfies the "stable while
the set is unchanged" guidance, as long as an adapter does not sort on the
way out.

## Compatibility matrix

| Spec surface | This repo | Gap |
|---|---|---|
| stdio or Streamable HTTP JSON-RPC | TCP newline JSON | No MCP client can connect |
| `server/discover` | `route:status` | Missing versions, capabilities, instructions |
| Per-request `_meta` protocol version | ignored | A modern client is speaking a different protocol |
| `tools/list` | `route:tools` | Rename `input_schema` → `inputSchema`; add `resultType`, `ttlMs`, `cacheScope`; optional cursor |
| `tools/call` | `route:call` | Map `output` to `structuredContent` plus a text block; map `success:false` to `isError: true`; unknown tool to JSON-RPC `-32602` |
| `tools.listChanged` | in-memory version only | Not advertised, not delivered |
| `subscriptions/listen` | connection closes after one response | Cannot host the stream on this socket |
| Annotations | absent | Defaults mark every tool destructive |
| `outputSchema` | absent | Hosts cannot type results for code-mode |
| Image / embedded resource content | `TakeScreenshot` returns a file path | Model does not receive pixels |
| Guides | `ListGuides` / `GetGuide` tools | Could also be resources; not required |
| Tasks extension | `GetResult` plus in-plugin async calls | Different protocol; useful later for `WaitUntil` and shadow bakes |
| `input_required` / elicitation | `dialogAfter` + `RespondDialog` | In-game dialogs are not the MCP user's form. Keep the current pair |
| OAuth, sampling, roots, logging | none | Do not add. Logging and sampling are deprecated; this socket is localhost with no auth (`SECURITY.md`) |

## How an agent should learn about a new pack

Spec path, once a real server exists:

1. Host calls `server/discover`, sees `capabilities.tools.listChanged: true`
   and a short `instructions` string (readiness, packs, guides).
2. Host calls `tools/list` and caches it for `ttlMs`, scope `private` (the
   catalog depends on which plugins are loaded in this game).
3. Host opens `subscriptions/listen` with `{toolsListChanged: true}`. The
   TypeScript SDK can do this via `client.listen` or the `listChanged` client
   option, which re-fetches `tools/list` on each notification.
4. Pack plugin calls `RegisterToolPack`. Adapter notices the generation bump
   and sends `notifications/tools/list_changed` on that stream only.
5. Host drops the cached list, re-lists, and re-indexes search. New tools are
   `packId.FuncName`. The host should append them rather than reorder the
   whole array, or prompt-cache prefixes get invalidated (client best
   practices, "Interaction with Prompt Caching").

Search stays in the host. This server should publish a good catalog (stable
order, names, descriptions, schemas, annotations) and the change
notification. It should not invent `tools/search` as the way agents discover
packs. A dumb host that never subscribes still sees new tools on its next
`tools/list`; it will not see them mid-turn.

Hosts that only implemented the pre-2026-07-28 habit of listening for an
unsolicited `list_changed` will miss pack loads until they open
`subscriptions/listen`. That is a client gap, not something the socket can
paper over.

## What to change

Keep JSON-RPC out of AngelScript. The game plugin should stay a tool registry
and a socket. A small stdio process should be the MCP server and should call
the socket the way `tools/call.py` does.

### 1. Adapter (the compatibility fix)

- Speak `2026-07-28`: `server/discover`, `tools/list`, `tools/call`,
  `subscriptions/listen`.
- Dual-era: also answer `initialize` for clients still on `2025-11-25` or
  earlier. Modern clients probe with `server/discover` first; a legacy-only
  server fails that probe (versioning compatibility matrix).
- Advertise `tools: { listChanged: true }`, `supportedVersions`, and
  `instructions` that point at `GetReadiness`, `ListToolPacks`, and `GetGuide`.
- Translate `input_schema` to `inputSchema`. Pass through the pack id in
  `_meta`, not as an extra Tool field.
- Map failed tool results to `isError: true` with the existing `error`,
  `code`, `hint`, and `retryable` in `structuredContent`. Unknown tool and
  malformed requests stay JSON-RPC errors.
- Set `cacheScope: "private"` and a short `ttlMs`. The list is per machine
  and per loaded plugin set.
- Hold `subscriptions/listen` open in the adapter. Ack the stream first
  (`notifications/subscriptions/acknowledged`, `subscriptionId` equal to the
  listen request id) and put that id on every later notification. Poll the
  socket for a generation counter. On change, emit
  `notifications/tools/list_changed` and let the host re-list.
- One plugin change belongs with this: include `toolListVersion` on
  `route:status`, sourced from `g_ToolListVersion`. The adapter can then poll
  a tiny payload instead of diffing the full catalog.

### 2. Make the catalog useful to hosts that do load tools

Worth doing in the adapter and, where the data does not exist yet, on the
tool definitions:

- `annotations.readOnlyHint` / `destructiveHint` for reads versus
  `ClearMapContent`, `ShutdownGame`, placement, and deletes. Without this,
  the spec default is destructive.
- `outputSchema` for the tools agents chain (`GetMode`, `GetReadiness`,
  `GetMapInfo`, placement results). Client best practices say code-mode
  hosts otherwise fall back to `any`.
- `structuredContent` set to today's `output` object, with a short text
  block beside it for older clients.
- `TakeScreenshot`: add an MCP image content block (bytes or a resource the
  host can read). A path string does not show the shot to the model.
- Split the essay-length descriptions. `tools/list` is what lands in
  context and in search indexes. Long operational notes can stay on
  `GetGuide`.

Do not add a server-side `SearchTools` as the discovery mechanism. Add one
only if a specific host we care about neither subscribes to `list_changed`
nor implements progressive discovery. That would be a host workaround, not
the spec path.

### 3. Later, and only if a host timeout forces it

- `io.modelcontextprotocol/tasks` for `WaitUntil`, `ComputeShadows`, and
  `CreateMapViaMenu`, which already outlive a casual RPC timeout. Return
  `resultType: "task"` only when that request declared the extension. For
  every other client, keep blocking or hand back the existing `GetResult`
  request id as an ordinary tool argument. Do not invent a second async
  protocol in AngelScript.
- Guides as MCP resources. The tools can stay.
- Pagination on `tools/list` once pack catalogs make a single response
  painful. Cursor can be an opaque offset. Order must stay stable across
  pages.

### Leave alone

- OAuth and public bind. `SECURITY.md` is the right threat model.
- Sampling, roots, logging. Deprecated, and they do not help Trackmania control.
- `input_required` for in-game dialogs. The person who can click Yes is at
  the game. `dialogAfter` and `RespondDialog` already express that.
- `x-mcp-header`. That is a Streamable HTTP intermediary feature. stdio
  clients may ignore it.
- Implementing the MCP session inside the Openplanet script. The socket's
  one-request connection and the render-thread budget are the wrong place
  for a long-lived JSON-RPC stream.

## Suggested sequence

1. Expose `toolListVersion` on `status`.
2. Ship a stdio adapter (dual-era) that lists, calls, and notifies.
3. Point Claude / Cursor / Codex at that process, not at port 30006.
4. Add annotations, `outputSchema`, and screenshot image content.
5. Revisit tasks if host-side timeouts still kill long editor waits.
